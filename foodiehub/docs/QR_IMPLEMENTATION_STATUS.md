# QR Dine-In Ordering Status

## COMPLETED AND VERIFIED

- Existing table foundation remains in `server/src/models/RestaurantTable.js`, `server/src/modules/restaurants/table.controller.js`, `table.routes.js`, and `20261116210000-create-restaurant-tables.js`. Owner-only token generation uses 32 cryptographically random bytes; the public resolver verifies active table, public restaurant and dine-in branch. Deactivation clears the token.
- Existing QR table menu uses `client/src/portals/customer/pages/QrMenu.jsx` and public `GET /api/v1/public/qr/:token`. It now opens existing `FoodItemDetails` to select variants/add-ons and add to the authenticated customer's existing cart. The token, rather than client table/restaurant/branch IDs, supplies the dine-in context to `POST /api/v1/customer/cart/items`.
- Backend validates the scanned token on cart add and revalidates the stored token hash and active table at checkout. Restaurant, branch, and table are derived server-side. Cart switching across restaurant/branch/table is rejected. Menu availability and option selections are repriced/validated by existing checkout logic.
- Table-bound cart response and customer cart/checkout UI show table number. Checkout forces `orderType=dine_in`; server rejects another order type for a table-bound cart. Existing COD and Razorpay paths, payment verification, retry idempotency, and cart-clear behavior are reused.
- Restaurant details now offers manual dine-in table selection scoped to the selected public branch. The backend lists active tables with an existing QR token and validates the selected table against restaurant, branch, and active status before returning that token for normal server-side QR resolution. The UI does not claim tables are available: occupancy tracking is not implemented.
- The existing owner Tables page now has a separate restaurant menu QR card (no table context), with download, print, copy, and open actions. Table QR modals provide individual download/print/copy/regeneration; Print QR sheet covers all active tables and creates tokens only for active tables missing a token. No duplicate navigation or QR model was added.
- Table tokens are generated with 32 cryptographic random bytes and `restaurant_tables.qr_token` is globally unique. In the configured database, 5 existing table tokens were all unique and all 5 resolved to the matching table and branch. Public restaurant QR requests for two restaurants returned distinct restaurant menu URLs with no table assignment. An invalid token returned 404; unauthenticated bulk and individual table QR management returned 401. Owner-authorized bulk/individual printing and regeneration were not exercised.
- `Order.tableId` and associations are defined. Customer order list/detail, restaurant order management, kitchen, and waiter responses/UI display the related table number. Existing restaurant/branch authorization and status transitions remain in place.
- Added the existing project’s Sequelize CLI migration `server/src/migrations/20261116220000-add-qr-dine-in-ordering.js`. It adds nullable cart `table_id`, `table_qr_token_hash`, order `table_id`, and `orders_table_status_idx`; guards avoid duplicate columns/indexes after partial MySQL DDL. Model fields map to `table_id` and aliases associate `Order`/`CustomerCart` with `RestaurantTable`.
- The configured development DB reports the QR migration as `up`. Read-only schema inspection confirmed `orders.order_type`, nullable `orders.table_id`, nullable `customer_carts.table_id`, nullable `customer_carts.table_qr_token_hash`, and `orders_table_status_idx(table_id,status)`. An ORM query selecting `Order.tableId` and `orderType` also succeeded with mappings to `table_id` and `order_type`. The earlier `Unknown column 'Order.table_id'` does not match the DB used for these checks; compare the running API's DB target with the CLI target. No migration was run during this pass.
- Verification: frontend production build passed; backend `node --check` passed. Live public API smoke checks against Pizza House confirmed the selected branch lists the table, selection returns an existing QR token, and selecting that table under the other branch returns 404. No authenticated cart/checkout or placed-order E2E was performed.
- The current task verification includes backend syntax checks and targeted frontend lint; no production rebuild was run per request. Generated QR PNGs were created by the existing `qrcode` encoder and route destinations/resolution were checked, but no installed QR decoder or physical camera scan was available. Browser print dialogs, copied links, owner authorization, and authenticated dine-in order placement remain unverified.
