# Customer Ordering Implementation Status

## Completed and verified

- Customer marketplace discovery is public at `GET /api/v1/public/restaurants`; restaurant details and branches use `GET /api/v1/public/restaurants/:slug` and `/branches`; public menu browsing uses `/menu?branchId=...`. These endpoints enforce published/approved restaurant and eligible branch visibility and return public fields only. See `server/src/modules/public/public.controller.js` and `client/src/portals/customer/pages/Restaurants.jsx`.
- Normal menu browsing does not require QR. `client/src/portals/customer/pages/RestaurantDetails.jsx` loads the selected branch menu and now has direct View menu and Order online links. Menu item details support variants/add-ons and add-to-cart through `client/src/portals/customer/components/FoodItemDetails.jsx`.
- Authenticated customer cart persists restaurant and branch scoped items. API: `GET/DELETE /api/v1/customer/cart`, `POST /api/v1/customer/cart/items`, `PATCH/DELETE /api/v1/customer/cart/items/:itemId`. Server reprices menu/options and rejects unavailable items or mixed restaurant/branch carts in `server/src/modules/customer/checkout.controller.js`.
- Checkout validates branch service, open hours, customer-owned delivery addresses and enabled payment methods. APIs: `GET /api/v1/customer/checkout/summary` and `POST /api/v1/customer/checkout/validate`. COD order creation and Razorpay order/signature verification are implemented in `server/src/modules/customer/checkout.controller.js`, mounted by `server/src/modules/customer/customer.routes.js`. Razorpay secrets remain server-side and branch online-payment opt-in is required.
- Generic customer order history/detail and tracking exist at `GET /api/v1/customer/orders` and `/orders/:orderId`, displayed in `client/src/portals/customer/pages/CustomerOrders.jsx` and `CustomerOrderDetails.jsx`. Existing project records report database-backed tests for repricing, cart isolation, COD idempotency, Razorpay verification guards and customer order ownership in root `IMPLEMENTATION_STATUS.md`.
- Existing public QR token resolver/page and owner QR controls are retained. QR menu item customization now uses the existing customer cart API and carries the scanned token; the server resolves table, restaurant, and branch from that token and stores a token hash with the cart context. Checkout forces dine-in for a table-bound cart and associates the order to the validated table. The migration is not confirmed applied, so these flows are not database-verified or complete.
- Added a separate on-demand branch menu QR endpoint: `GET /api/v1/public/restaurants/:slug/branches/:branchId/qr`. It encodes the existing public `/restaurants/:slug?branchId=...` URL and reuses marketplace eligibility checks and shared `PUBLIC_APP_URL` validation. It does not create or modify table tokens.
- Customer restaurant details at `client/src/portals/customer/pages/RestaurantDetails.jsx` now has a selected-branch QR modal with preview, PNG download, Web Share API (sharing the image when supported), clipboard URL fallback and Open Digital Menu link.
- This pass verification: frontend production build succeeded; frontend lint exited successfully with warnings; changed server files passed `node --check`. A live read-only API check verified one eligible branch's QR payload points to the same slug/branch as its public detail page, an unpublished restaurant was rejected (404), an existing active table token continued resolving (200), and unauthenticated table management returned 401. A malformed QR token returned 404.

## Implemented but not fully verified

- The newly added restaurant-detail View menu/Order online links and QR menu option display passed production compilation but were not manually inspected in desktop/mobile browsers.
- The customer QR endpoint returned a real PNG data URL for one eligible branch. The new modal's browser display, download click, native share/clipboard behavior and QR scan were not manually exercised. Only one eligible branch was available, so multiple-branch switching is not integration-tested; no inactive branch record was available for an inactive-branch API test.
- Owner QR token generation, PNG download, valid-token menu data, correct restaurant/branch/table display, token rotation/revocation, and option rendering against a real table/menu were not exercised with an authenticated owner and live customer browser.
- Delivery order creation is supported as a fulfillment type, but actual delivery coverage is explicitly unverified (`deliveryCoverageVerified: false`). Delivery fee, tax, packaging fee and coupon configuration are absent and currently zero; do not treat checkout as a dispatch/fee engine.
- Takeaway order creation is supported, but scheduled pickup time and collection handoff states are not implemented.
- COD and Razorpay availability are branch-level, not separately configured per fulfillment type. Dine-in uses the existing payment flows, but QR dine-in payment and cart clearing have not been exercised end to end.
- Customer tracking refreshes/polls order state; no verified push/realtime customer status delivery exists.
